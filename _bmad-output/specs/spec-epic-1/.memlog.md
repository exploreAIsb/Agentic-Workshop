- (capability) CAP-1 a triage decision can be represented and validated as one JSON object: category (billing|bug|access|performance|how-to), priority (P1-P4), route (billing-team|bug-team|access-team|performance-team|how-to-team) and a one-sentence rationale; success: a conforming object validates, and anything else (missing field, bad enum value) is rejected with a clear error
- (capability) CAP-2 a person loads the seed data into a local SQLite database with one command; success: uv run python load_seed.py reads seed/tickets.csv and seed/customers.csv into app.db as tables tickets and customers with the same columns as the CSVs, and running it twice leaves app.db in the same state
- (constraint) seed/ is read-only -- the loader may read seed/tickets.csv and seed/customers.csv but never write to them
- (constraint) no network calls and no API keys in this epic -- schema validation and the loader are local-only
- (constraint) mcp/triage_server.py already queries app.db (SELECT ticket_id, customer_id, created_at, text FROM tickets; SELECT customer_id, name, plan, open_tickets FROM customers) and is read-only; load_seed.py's tables and column names must keep those queries working
- (non-goal) the agent, the MCP tools, evals and any user interface are out of scope (Epic 2 and Epic 3)
- (assumption) the schema validates category, priority and route as independent enums per INTENT.md's literal field lists; it does not enforce that route matches category's TRIAGE_POLICY.md mapping (billing->billing-team etc.) -- that pairing is policy logic the Epic 2 agent applies, not a schema-level constraint
